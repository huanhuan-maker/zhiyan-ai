- **交付节奏**：M0→验收→M1→验收→M2→验收→M3→验收→M4→验收→M5→验收→M6。
- 每阶段必须提交：源代码变更、数据库迁移（如有）、测试代码、实际执行的命令及结果、`evidence/Mx.md`、已知问题、下阶段风险。
- 不得用截图假装系统工作，也不得用固定假数据代替真实 MySQL CRUD。AI 的 Mock 模式必须醒目标注，不计作真实大模型能力。

## 1. 范围冻结：要做和暂时不做

### 1.1 V1.0 必须完成的用户旅程

1. **调研发起者**：注册/登录 → 输入调研意图或手工建卷 → 审核编辑题目 → 设置调查与追问预算 → 发布问卷 → 查看回收进度 → 复核新主题 → 查看 ECharts 统计及来源明确的报告。
2. **受访者**：打开分享链接（无需账号）→ 阅读告知并选择是否参与 AI 追问 → 填写核心题 → 在开放题后按需收到一条中立追问或直接继续 → 可跳过追问 → 提交成功。
3. **研究验证**：可固定随机种子/测试样本，使用 A/B/C/D 四种策略对照，导出匿名事件，复算核心指标。

### 1.2 V1.0 题型与问询边界

- 核心题型：单选、多选、量表、开放填空；第一阶段重点研究**开放题**追问。其他题型仅预留后续追问接口，不强求第一版都支持动态追问。
- 允许追问动作：`SKIP`（跳过）、`CLARIFY`（澄清）、`DEEPEN`（深入）、`EXPLORE`（沿受访者自己提出的相关新线索探索）。
- 追问需要同时考虑：与调研目标相关性、信息缺口、有效信息预计增量、个人负担、剩余总预算、诱导风险。
- 追问预算示例默认值：每道开放题最多 1 次，全问卷最多 3 次；可由发起者修改。**这是产品默认参数，不是已证明最优的参数。**
- 固定核心问卷发布后冻结；动态追问回答单独存储；跨受访者新主题**不自动回写已发布问卷**。
- 新主题证据区分：自发提出、AI 中立追问后补充、选项提示后确认、模型推测未确认。
- Jev 为可选决策适配器；必须有规则/LLM 替代机制，未连接 Jev 不影响系统主流程。

### 1.3 本轮排除

完全聊天式调查、复杂企业 SaaS 计费、问卷市场、医疗诊断、调查中自动改变核心题目、调查期间自动跨受访者验证假设、未经授权的数据抓取。

## 2. 强制技术与设计原则

| 模块 | 指定技术 | 开发要求 |
|---|---|---|
| 前端主框架 | **Vue 3** | 推荐 TypeScript、Vite、Vue Router、Pinia；单页应用，移动端适配。 |
| 图表 | **Apache ECharts** | 在统计页真实渲染 MySQL 数据；图表自适应，正确 `resize` 与 `dispose`。 |
| 服务端 | **Spring Boot** | 推荐兼容 Java 17+ 的 Spring Boot 3.x 稳定组合；REST API，参数校验、错误处理、鉴权。 |
| ORM/Mapper | **MyBatis-Plus** | 使用 Spring Boot 3 对应 Starter、`BaseMapper` / LambdaQueryWrapper 等；**不得用 Spring Data JPA**。复杂统计允许经过参数化处理的 Mapper SQL。 |
| 数据库 | MySQL 8.x | 提供初始化/迁移 SQL、测试数据和备份说明；持久化真实数据。 |
| AI 服务 | 可替换 Provider | 服务端调用；密钥只在服务端环境变量；限流、超时、JSON Schema 校验、失败降级。 |
| 测试 | JUnit 5 + Spring Boot Test；前端 Vitest 可选；Playwright 可选 | 至少服务端集成测试与关键路径端到端验证；不能全部只靠手测。 |
| 部署 | Windows 本地可启动，Docker 可选 | `README` 要提供无需 Docker 的启动路径；命令在 PowerShell 下可复现。 |

MyBatis-Plus 官方 Spring Boot 3 坐标示例：`com.baomidou:mybatis-plus-spring-boot3-starter`；不应与另一套 `mybatis-spring-boot-starter` 重复引入。**具体版本由 Agent 查官方兼容矩阵后锁定并记录在版本清单中**。

## M0｜工程骨架与环境联通

**开发目标**：消除“在 Agent 的环境能跑，在自己 Windows 上跑不了”的问题。

**开发任务**
1. 建立 `frontend/`、`backend/`、`db/`、`docs/`、`evidence/` 等目录；Git 初始化或适配既有仓库。
2. Vue 3 + TypeScript + Vite 页面骨架：登录页、发起者工作台、公开答题页、统计页（可为真实空状态，不得伪装功能完成）。
3. 安装 ECharts，实现一个明确标记为“开发环境联通演示”的简单图表，M1 改为真实接口数据。
4. Spring Boot 服务，MyBatis-Plus 配置、`@MapperScan`，MySQL 8 连接；创建一张 `system_checks` 测试表，验证经 Mapper 插入/读取记录；写完可保留为健康诊断示例或移除。
5. 环境配置模板：`.env.example`、后端 `application-local.yml` 及启动说明；不上传密钥/数据库密码；基础错误响应与健康检查。
6. 发起者登录会话与最小权限框架（若暂未完整实现，要确保 M1 补齐）。

**Agent 必交付**：安装说明、可复制的 PowerShell 命令、依赖版本表、数据库建表/迁移脚本、健康检查示例、至少 1 项 MyBatis-Plus 真实 SQL 集成测试、截图或录屏。

**你怎样验收**
- `npm install`、`npm run dev`、`npm run build` 正常；打开首页无空白或致命错误。
- 后端 `./mvnw.cmd spring-boot:run`（或仓库实际 Maven Wrapper 命令）成功；访问 `/actuator/health` 或文档指定路径得到成功健康状态。
- MySQL 存在测试记录，停止服务后重新启动仍能读到。
- `pom.xml` 确有 MyBatis-Plus Starter、没有 JPA；`package.json` 有 `vue` 和 `echarts`。

**禁止进入 M1 的情况**：数据库仅使用内存临时表、应用必须有 AI Key 才启动、Maven 测试失败、前端只有静态原型。

## M1｜不用 AI 的真实问卷闭环

**开发目标**：先把“问卷工具”做成能用的软件。

**开发任务**
1. 调研发起者注册/登录、草稿列表、创建问卷、编辑四种题型、预览、发布及关闭调查。
2. 发布生成不可变版本、唯一随机公开链接；旧版本结果不因新版本草稿修改而改变。
3. 匿名受访者可以打开链接、阅读告知、填写、提交；支持必填校验、可选答案、离线/刷新适当恢复及提交成功状态。
4. 后端用 MyBatis-Plus 完成真正的问卷、题目、版本、会话、答案持久化；提交事务和幂等保护。
5. 发起者看到回收人数、按题选项统计；首个 ECharts 柱状图/饼图展示**真实接口数据**。
6. 访问权限：别人不能编辑/查询我的调查；公共链接不能读其他受访者的答案或发起者统计。

**Agent 必交付**：`survey` 相关数据库迁移与 Mapper/Service/Controller、前端实际交互、M1 自动化测试、演示问卷数据、公开链接与相关接口契约。

**你怎样验收（十分钟手工流程）**
1. 创建题为“食堂满意度”的调查：一道单选（满意/一般/不满意）、一道多选、一道 1–5 量表、一道开放题；保存并刷新，内容不丢。
2. 发布复制链接，在手机浏览器或浏览器移动模拟器里填写。用两个独立会话分别提交“满意”和“不满意”。
3. 回工作台看到**回收数=2**，单选各为 1 人/50%，ECharts 数据与记录一致；刷新统计页不变化。
4. 再点一次提交，回收数不得变成 3；换一个账户访问该调查管理地址必须被拒绝。
5. 发布后修改草稿：旧分享链接加载旧版内容，旧答案仍绑定原版本。

**验收失败例子**：ECharts 中写死 `50,50`；刷新后问卷不见了；同一个会话可重复计数；通过公共链接能看到后台数据。

## M2｜AI 问卷草稿设计（为核心研究建立调查基础）

**开发目标**：用户输入想调查什么，AI 输出可编辑、可审核的结构化问卷；**AI 不可以直接绕过审核发布**。

**开发任务**
1. 发起者输入调查目标、目标人群、可选补充信息、期望题数；AI 可以就关键模糊点问简短澄清。
2. 后端 AI Provider 生成严格 JSON 结构（题型、题目、选项、变量、必填标识、是否允许追问、预设调查维度）。
3. 服务端检查 Schema、题型合法性、量表范围、选项唯一性、选项是否明显缺失、逻辑不一致、重复及明显诱导性表述；未通过的草稿不允许发布。
4. 人工编辑、预览、保存，发布机制复用 M1；AI 超时/无密钥时仍可手工建卷。
5. 显示提供者/模型/Mock 状态；服务端不得记录原始 API Key，避免将未经授权的回答传给外部服务。

**你怎样验收**
- 输入“调查大学生为什么不参加社团”，生成包含合适的结构化题型和一项开放题的草稿；人工修改后发布。
- 输入空白、无效数量、明显含糊的目标，系统提示澄清或给出合理错误，不崩溃。
- 人为使 AI 返回损坏 JSON/非法题型/重复选项，服务端拒绝并可手工修正。
- 未设置真实 AI Key 时，页面不得假称“真实 AI 已生成”；基本问卷功能仍可用。

**闸门**：结构化草稿可编辑并真正保存；无未经校验直接写数据库/发布的模型输出。

## M3｜单人主动深度探索（项目核心一）

**开发目标**：使 AI 不仅能追问，还能依据目标、当前信息和预算主动判断何时澄清、深入、探索或停止。

**开发任务**
1. 后端状态机 `CORE_ANSWER_SAVED → EVALUATING → SKIP/ASK → REPLIED/DECLINED/TIMEOUT → NEXT_QUESTION`，所有决策和转移入库。
2. `FollowUpDecisionProvider` 统一接口：第一版实现 RuleProvider + 可选 LlmProvider；JevProvider 暂保留契约，不要求在此阶段接通。
3. 根据上下文候选 `CLARIFY/DEEPEN/EXPLORE/SKIP`；`EXPLORE` 必须基于受访者**自己提出**的新线索，不得凭空塞入动机。
4. 硬约束先于模型：用户同意、拒绝/跳过、话题相关性、每题/全卷预算、隐私风险、已追问次数、模型失败。失败应继续下一题，不可卡住。
5. AI 生成一条中立追问；服务端校验合法性及重复风险，不合格则降级跳过或有限重试。
6. 记录追问的依据、源回答、动作、策略/模型版本、展示文本、回应、跳过原因、用时与成本估算。原答案不可被追问覆盖。
7. 前端保持问卷为主体：追问仅嵌在开放题下方，清楚提供“回答”“跳过”。

**你怎样验收：至少 6 组确定性用例（规则/Mock 可重复）**
- **模糊**：“食堂不太方便”→ 可以澄清具体不便，不能断言一定是价格或卫生。
- **具体**：“六点二楼排队十五分钟，菜经常卖完”→ 允许 `SKIP`，若探索需有真实理由，不能仅以字数判断。
- **新线索**：问图书馆使用原因，受访者说“朋友都不去”→ 可探索“同伴影响”，不能说是受访者未提到的其他动机。
- **跳过**：受访者点击跳过→ 不再重复弹同一追问，原回答保留。
- **预算**：全卷上限为 2 时，最多出现 2 次追问；刷新/重试不得重复扣减。
- **超时/无 Key**：问卷依然能继续并提交，日志记录降级原因。

**闸门**：六组能复现；数据表可查看每次决策理由；没有“所有回答都追问”的假智能行为。

## M4｜跨受访者新维度发现（项目核心二）

**开发目标**：从不同人的回答中提取原问卷未覆盖的相关主题，但不把 AI 猜测当成事实。

**开发任务**
1. 已完成、同意分析的答卷经异步/批处理抽取语义单元；去重、归并相似表达、与预设维度比较。
2. 每条候选主题存储 `theme_evidence`：匿名会话、题号、原始或追问文本位置、来源类别。
3. 强制区分 `SPONTANEOUS / NEUTRAL_PROBE / SUGGESTED_OPTION / MODEL_INFERRED_UNCONFIRMED`，未确认的推测不能算受访者观点。
4. 主题复核台可“接受、重命名、合并、驳回”，操作有审计记录；主题结果不修改当前已发布核心题。
5. 主题频次使用独立**受访者数**而非引用片段条数；分开报告不同来源，展示符合统计定义的分母，不滥用代表性措辞。

**你怎样验收**
- 在“图书馆原因”调查里，预设维度只有环境、座位、开放时间，导入至少 8 份模拟答卷，其中数份主动提到“朋友不去/结伴不方便”，另有不相关主题。
- 系统能提出“同伴影响”之类的新候选维度，点击后看到每条**确实存在**的原始证据。
- 两个相近提法聚合而不简单按词面拆分；同一个人说两次不能当成 2 个人。
- 手工驳回或合并后，再刷新仍保留审核结果；发布版核心题未改变。
- 即使模型输出虚构引用 ID，也不能落到“有真实引用”的主题中。

**闸门**：主题证据可逐条核对、来源可区分、人工审核生效、无捏造原文。

## M5｜ECharts 数据分析与可信报告

**开发目标**：让不懂统计的发起者也能读取结果，同时保证分析数字可复核。

**开发任务**
1. 选择题、量表题、多选题、缺失值和版本分组统计由 Spring Boot + MyBatis-Plus/参数化 SQL 计算；说明分子、分母、过滤条件。
2. ECharts 展示单选分布、量表分布、多选比例、回收趋势；必须从接口读数据，窗口大小变化正常渲染、组件卸载销毁实例。
3. 开放题主题分析与原文证据独立呈现；标注自发/中立追问/提示后确认的来源。
4. 生成报告：**事实统计块 → AI 解释块 → 待验证假设块**；AI 只解释确定性计算，不准编造数字。
5. 可导出 CSV（匿名/字段脱敏/明确编码）；HTML/Markdown 报告可作为 V1 产出，PDF 留到后续。

**你怎样验收**
- 使用已知分布的 10 份测试答卷，例如 6 人选 A、3 人选 B、1 人未回答：**该题有效分母 9** 时为 66.7% 与 33.3%；如果展示总样本口径必须明确另行标记。注意“未回答”是否允许取决于题目必填设置。
- ECharts 图上每个数与 SQL 查询/导出数据一致；刷新、筛选、浏览器缩放都正常。
- 多选题的各选项比例可以合计超过 100%，并明确“按有效人数计算”；不错误地强制加总到 100%。
- 点击报告一句结论，应能跳到对应统计块或真实匿名引用；数据不足时显示无法推断，而不是胡编。

**闸门**：存在可重复计算的统计测试；图表不是静态示例；报告没有无依据结论。

## M6｜对照评估、质量回归及演示交付

**开发目标**：不仅完成产品，还能给比赛评委解释“为什么这种追问更好”。

**开发任务**
1. 策略开关：A 固定问卷；B 普通 LLM 自由追问（相同预算）；C 受约束澄清/深入；D 本项目的受约束主动探索+全局预算。Jev 若有稳定接口和额度，可作为 E 消融组，不是毕业/参赛的必需依赖。
2. 建立至少 3 个不同场景的合成测试集（校园、消费、公共服务等），文档明确数据为合成；准备人工评估表、独立盲评流程。
3. 收集客观工程数据：每人有效新增语义单元、每次追问增量、无效/诱导性问题比率、平均答题耗时、退出/跳过率、主题证据有效率、AI 调用延迟与成本。
4. AI 自评不得作为唯一证明；人类评估需记录标注员、标注说明与一致性。真实受访者实验应自愿参与、清楚告知，并谨慎处理个人数据。
5. 回归与安全测试：跨账户权限、恶意输入、过期链接、断网/AI 超时、数据库重启、重复提交；检查敏感日志和 API Key。
6. 提供比赛演示材料：演示账户/合成案例、演示脚本、系统架构图、对照实验表、创新边界与已知局限。

**你怎样验收**
- 用相同数据和固定配置两次运行评估脚本：统计口径稳定，随机部分记录种子/模型版本，不伪称完全确定。
- 至少能展示“为什么触发某次追问”“该追问后实际新增什么”“如何确定跨人主题及证据来源”。
- 断开 AI 服务：基本问卷仍可使用；未通过校验的模型输出不入库。
- Windows 从空白环境按文档安装、启动、演示，另一位同学也可复现；失败项在 README 如实说明。

**闸门**：功能、测试、说明与实验材料齐全；没有把 Mock 演示当成真实算法成绩。

## 4. 阶段质量门槛（每阶段相同）

1. **真实代码**：代码文件存在，页面按钮接通实际接口；无纯静态占位冒充完成功能。
2. **可运行**：Windows PowerShell 环境按照 README 启动，前后端通、数据库有持久化记录。
3. **可验证**：自动测试命令能执行，日志里有通过数和失败数；至少一项手工全流程复现。
4. **可解释**：影响用户的 AI 决策有来源、理由和失败处理；统计数字来自程序计算。
5. **可追责**：谁改了问卷、哪个版本、谁审核主题、回答来自哪里均有记录。
6. **可交接**：`evidence/Mx.md` 写明完成/未完成、启动命令、测试结果、截图链接、遗留问题。
7. **可停止**：当前验收失败时 Agent 修复当前阶段，不引入下一阶段需求掩盖问题。

## 5. 验收决策表（你和 Agent 都遵循）

| 结果 | 判定 | 下一步 |
|---|---|---|
| 功能演示 + 自动测试 + 安全检查全部过 | PASS | 保存 Git 提交与证据，进入下阶段 |
| UI 看似能用，但数据不持久化/访问越权/重复提交 | FAIL | 必须修复，不能进入下一阶段 |
| 只有 Mock AI，且本阶段要求真实 AI | FAIL | 配置真实 Provider 做测试；无密钥则记录阻塞，不可假报 |
| 外部 AI 暂不可用，但当前阶段明确允许降级 | CONDITIONAL | 基础功能可以过，标明真实 AI 子项未过 |
| 证据无法核查/Agent 只贴“测试成功”一句话 | FAIL | 要求给出命令、实际摘要、可复现步骤 |

## 6. 论文与答辩的评价边界

- “能自动追问”“有 AI 报告”不是创新性证明；必须和固定问卷、普通 LLM、受约束追问基线公平比较。
- 新主题来源不能混淆；“提到某主题”不等于“总体有该观点的比例”，更不等于因果结论。
- Jev Choice 的模型分布不等于信息增益或真实人群概率；加入 Jev 必须证明其额外价值。
- 若实验结果不佳，应如实报告并调整算法，不为比赛虚构提升百分比。
