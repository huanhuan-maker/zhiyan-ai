# 知研 AI｜Windows 本地验收操作手册 V2.0

> 适合没有丰富测试经验的学生。按顺序执行，**每个阶段只验收已经交付的功能**。如果开发 Agent 写的端口/脚本和示例不同，以项目真实 README 为准，并要求 Agent 说明差异。

## 0. 一眼就能判断有没有“真做”的三个原则

1. **刷新不丢数据**：问卷、答案、审核记录、统计结果必须来自真实持久化数据库，不是浏览器临时变量。
2. **换用户/换设备有区别**：发起者 A 的问卷不能被发起者 B 修改；公开问卷链接允许受访者填写，但不能看到其他人的答案。
3. **AI 结果要可核查**：让 Agent 告诉你模型是否真实连接、用的是哪个 Provider、为什么追问、某条新主题来自哪句话。禁止用“模拟结果”和样例图片冒充真正完成。

## 1. 最初安装和环境核查（Windows 10/11，PowerShell）

请开发 Agent 把**安装清单、推荐版本、官网链接、启动命令**写进最终项目的 `README.md`。你先打开 PowerShell 运行：

```powershell
node -v
npm -v
java -version
mysql --version
# 如果用 Docker 启 MySQL，再检查：
docker --version
docker compose version
```

- 预期：Node、npm、Java 均能返回有效版本；MySQL 命令和 Docker 二选一即可，以 Agent 交付的数据库方案为准。
- 如果运行 `java -version` 提示“不是内部命令”，需要先安装 Java JDK 并配置 PATH；**不要因报错就让 Agent 删除 Spring Boot**。
- `mvn` 不一定需要全局安装，因为项目应该提交 `mvnw.cmd` Maven Wrapper。
- 前后端启动步骤应在项目根目录 README 中明示，不应依赖开发 Agent 私有机器的路径。

## 2. 启动项目：必须亲手操作一次

**终端 A：启动数据库**（只有项目采用 Docker Compose 时使用）

```powershell
docker compose up -d db
# 服务名称可能不同，使用仓库中的 compose.yaml 为准
docker compose ps
```

**终端 B：启动后端**

```powershell
cd backend
.\mvnw.cmd clean test
.\mvnw.cmd spring-boot:run
```

**终端 C：启动前端**

```powershell
cd frontend
npm ci
npm run build
npm run dev
```

说明：如果仓库还没有 lockfile，首次应 `npm install` 生成并提交后，后续使用 `npm ci`。示例端口通常是前端 `http://localhost:5173`、后端 `http://localhost:8080`，**以实际控制台输出为准**，不要硬编码假设。

**观察点**
- Maven 运行测试结束后显示真实通过/失败结果。`BUILD SUCCESS` 不是所有业务都正确的证明，只能说明被执行的构建任务成功。
- 前端 `npm run build` 正常结束，没有编译错误。
- 浏览器访问页面不出现空白屏；F12 → Console 无持续报错；Network 中 API 是真实 HTTP 请求，不是全页面都调用假数据对象。
- 重启后端和刷新浏览器后，已保存的问卷/答卷依然存在。

## 3. 框架是否符合老师要求？（M0 必做）

在项目根目录检查：

```powershell
Get-Content .\frontend\package.json | Select-String '"vue"|"echarts"'
Get-Content .\backend\pom.xml | Select-String 'spring-boot|mybatis-plus|spring-boot-starter-data-jpa|hibernate'
```

**合格标准**：
- `vue` 是 3.x 系列，前端代码确实写 Vue 组件；存在并实际使用 `echarts`。
- `pom.xml` 引入 Spring Boot 与适配当前 Spring Boot 大版本的 **MyBatis-Plus Starter**，Mapper/Service 真正参与数据库读写。
- 不应使用 Spring Data JPA 或 Hibernate 来实现主要数据持久层；不能只有依赖声明而业务实际全部走另一套 ORM。
- 检查 `backend/src/main/java/.../mapper/` 的真实 Mapper 类（或项目对应目录），例如 `SurveyMapper extends BaseMapper<SurveyEntity>`。
- 如果使用 Spring Boot 3，MyBatis-Plus 官方 Starter 名通常是 `mybatis-plus-spring-boot3-starter`；具体版本由项目锁定并记录。

**给 Agent 的修复口令**：
> 当前技术栈验收不合格。老师要求 Vue3+ECharts，Spring Boot+MyBatis-Plus。请列出不合格文件，修改实现并运行完整构建/集成测试。不要用其他持久层框架替代。

## 4. 阶段化手工验收剧本

### M0｜工程联通

- [ ] 网站能打开，页面不是白屏。
- [ ] 后端健康接口响应，前端能调用一个真实后端接口。
- [ ] 能通过 MyBatis-Plus Mapper 向 MySQL 写入一条测试记录，并读取回来。
- [ ] 重启服务后数据库记录没有消失。
- [ ] 错误的数据库配置应该有明确错误提示，不应悄悄用假数据库顶替。
- [ ] 环境变量模板可见；仓库里没有真实密钥。

**你要保留的证据**：前端截图、后端启动输出、Mapper 集成测试结果、MySQL 表查询结果。

### M1｜创建、发布、填卷、统计（核心端到端）

1. 以发起者身份登录，创建“食堂满意度测试”，添加单选（满意/一般/不满意）、多选（价格/口味/排队）、1–5 量表、开放题。
2. 保存草稿 → F5 刷新。逐题文本、顺序和选项仍正确。
3. 点击发布。复制分享链接，在浏览器无痕窗口打开；公开链接不要求以发起者登录。
4. 提交受访者 1：单选“满意”，量表 4 分，开放回答“中午排队慢”。
5. 新开无痕会话/新手机浏览器提交受访者 2：单选“不满意”，量表 2 分，开放回答“菜有时会卖光”。
6. 回到管理端刷新。预期：**有效提交数 2**；单选“满意”1 人、“不满意”1 人；图表与统计表一致；量表均值若按简单算术平均为 **3**。
7. 尝试刷新提交成功页并再次提交同一会话。预期：不会变成 3 份。
8. 使用另一个发起者账号访问当前调查后台 API。预期：被拒绝（403 或资源不暴露；不得成功返回私人答卷）。
9. 试着在发布后改题目。预期：不能篡改当前已发布版本；若支持重新发布，应产生新版本。

**关键追问 Agent 的问题**：“这些数据存在哪些 MySQL 表里？请给我各表字段和这一条答卷的关系，不要暴露敏感 token。”

### M2｜AI 创建问卷（首次真实模型）

1. 输入“我想研究大学生为什么不想参加社团，包含没参加过和已经退出两类人”，点击 AI 生成。
2. 检查生成的是**可编辑题目**而不是一张图片或一段不可修改的 Markdown；至少包含一题开放题。
3. 修改题目文本和选项，刷新草稿不丢失；发布后公开端一致。
4. 输入歧义较大的调研目标，AI 应能追问澄清或提供可审核的假设，而非随意武断决定目标人群。
5. 人为让模拟 Provider 返回错误 JSON：后端应给出可恢复提示，**不得把损坏草稿直接发布**。
6. 关闭 AI Key：应提示未配置真实 AI，但手工建卷、填写、提交仍然正常。

**合格的真实 AI 证据**：Agent 在本机显示 Provider 名称与模型版本、成功响应结构、失败处理。**不要让它把 API Key 或完整隐私回答发到聊天里。**

### M3｜自适应追问（最高优先级）

准备同一个开放题“你认为食堂哪里需要改善？”、题目和全卷追问上限。

| 用例 | 你输入 | 正确表现（不是唯一固定句式） |
|---|---|---|
| 模糊澄清 | 食堂不太方便 | 中立澄清“哪里不方便”或有理由跳过；不能凭空认定卫生差 |
| 具体描述 | 六点二楼排队十五分钟，轮到我时菜卖完了 | 可判断信息已经具体并 SKIP；如进一步探索须有记录的理由 |
| 新线索 | 图书馆调查中“我朋友都不去，所以我也没动力去” | 可探索“朋友影响”，不得捏造其他原因 |
| 自主跳过 | 点击跳过追问 | 直接进入下一题，原回答保留且不再弹出同一追问 |
| 全卷上限 | 设置全卷 2 次追问 | 无论多少开放题，最多显示 2 次；重复请求不额外扣预算 |
| AI 超时 | 暂停 AI 服务或用 Mock 模拟超时 | 能继续正常提交，系统记录降级 |
| 拒绝 AI | 受访者不同意 AI 追问 | 不向 AI 发送回答进行追问决策，仍允许填写问卷 |

**必须检查**：
- [ ] 追问只出现一条可理解的问题；不是连续生成一长段多问句。
- [ ] 提示剩余次数/可跳过；追问不覆盖原答案。
- [ ] 查看开发环境的追问决策记录：`action`、`reasonCode`、`sourceAnswerId`、`budgetRemaining`、策略版本均有。
- [ ] **不要只凭“回答字数小于 N 就追问”作为算法**；至少具备真实语义类别/约束判断。

### M4｜跨受访者新主题发现

使用合成数据（可让 Agent 提供 `seed` 脚本；不要拿真实隐私数据测试）：

- 原问卷调查“为什么不去图书馆”，预设因素只有“座位、环境、开放时间”。
- 8–12 份虚构答卷里，3 人自发描述“朋友不去/缺少结伴学习”，2 人说“排队/座位”，其余为其他主题。
- 启动主题发现；预期产生类似“同伴影响”的**候选新主题**，但不会直接宣称为群体普遍事实。
- 点击“同伴影响”，应该看到相应匿名答卷、题号、逐字原文或准确片段。
- 同一受访者说两遍不计为两名独立受访者；单纯 AI 猜测的理由不记为受访者实际提出。
- 接受、重命名、合并、驳回一个主题并刷新，审核状态保留。
- 打开已发布问卷，题目并未因为主题发现而自动变化。

**反作弊检查**：要求 Agent 修改一份种子数据里的“朋友不去”为“离宿舍太远”，重新分析。结果应随数据合理变化，不能永远硬编码输出“同伴影响”。

### M5｜统计图和 AI 可信报告

- [ ] 图表必须是 ECharts（检查源码的 `echarts.init` / ECharts 组件调用），不是截图、纯 CSS 饼图或外部仪表盘嵌入。
- [ ] 修改回收数据后 ECharts 刷新结果会变，图表与后端 API 一致。
- [ ] 单选题有效分母、未回答数量、问卷版本清楚。
- [ ] 多选题各选项占比合计允许大于 100%，口径写清。
- [ ] 主题报告区分自发提到/追问补充/提示后确认；给出可点击原文证据。
- [ ] 报告中的百分比必须能复算。例如“6/9=66.7%”，不是 AI 随机编出来的。
- [ ] 没有足够数据时，不应输出“所有人都认为”“显著提高”等过度推断。
- [ ] 页面缩放、切换标签后 ECharts 不消失；导出 CSV 后中文不乱码、字段与结果匹配。

### M6｜论文实验与最终答辩

- [ ] A/B/C/D 各策略都能在同一数据集和相同预算下运行；真实 AI 参与的部分说明其随机性。
- [ ] 每次追问都有动作、理由、耗时与模型调用记录；每条新主题都有证据。
- [ ] 人工标注的“有效新增信息”不由被评模型自己独立决定。
- [ ] 生成表格：有效新信息/追问、不必要追问率、诱导性追问率、完成/退出率、新主题证据支持率、耗时/成本。
- [ ] 重复运行可以复算统计口径；不能保证相同的 LLM 文本时应保存版本、输入与随机设置。
- [ ] 断网/关闭 AI/数据库重启后核心系统基本功能可用或有明确恢复机制。
- [ ] 可以由组内另一名成员照 README 从头搭建并完成演示。

## 5. 自动化测试：怎样看 Agent 有没有跑？

让 Agent 每阶段至少执行并贴出真实结果：

```powershell
# 在 backend 目录
.\mvnw.cmd clean test

# 在 frontend 目录
npm run build
# 若 package.json 提供单元测试脚本：
npm run test
# 若有端到端脚本，按项目 README 执行，例如：
npm run test:e2e
```

**你要看到**：执行目录、命令、退出码、通过/失败测试数、测试报告位置、失败时的错误摘要。只贴“测试已通过”而没有任何输出和代码变更，视为证据不足。

至少需要覆盖以下异常：
- `[ ]` 问卷被关闭仍可提交？应被阻止；
- `[ ]` 非当前所有者修改他人问卷？必须拒绝；
- `[ ]` 伪造或过期受访者 Session？必须拒绝；
- `[ ]` 重复点击提交、网络重试？不重复计数；
- `[ ]` 超出追问预算？禁止且不多扣；
- `[ ]` AI 输出无效 JSON / 超时？降级；
- `[ ]` 没证据的跨人主题？不能展示为“有证据的新发现”；
- `[ ]` 报告分母和版本混淆？必须修正。

## 6. Agent 每次交付时，你必须向它索要的东西

```text
请按当前阶段提交“验收证据包”，不要开始下一阶段：
1. 本阶段完成了哪些功能，哪些没有完成；
2. 修改的文件列表与最新 Git commit ID；
3. Windows 本地启动命令，以及我能访问的页面路径；
4. 数据库新增的表/字段与迁移脚本；
5. 实际执行过的自动测试命令、通过数、失败数与日志摘要；
6. 按本阶段验收剧本演示一遍，提供截图/录屏的保存路径；
7. 说明是 Real AI 还是 Mock AI；如果是 Real AI，说明服务提供者和模型版本（不得输出 Key）；
8. 安全或未完成问题清单；
9. 自检结果：PASS / FAIL / CONDITIONAL。不要声称已获我的最终验收。
```

**验收判定**：每个阶段你自己实际操作成功，测试也通过，才回复 Agent“通过 Mx 验收，允许实施 Mx+1”。

## 7. 发现问题后怎样让 Agent 修复？（复制即可）

```text
M__ 阶段没有通过验收，请停留在当前阶段，不要开发下一阶段。
失败复现步骤：1.__ 2.__ 3.__
实际结果：__
预期结果：__
控制台/接口报错：__
请先定位根因，再进行最小范围修复；补充能复现此问题的自动化回归测试。
完成后重新执行全部当前阶段测试，报告代码差异、测试结果和新的复验步骤。不要仅修改 UI 文案来掩盖后端问题。
```

## 8. 非功能检查（比赛演示前必须过）

- **隐私**：不默认收集实名；公开答题页面有数据用途和 AI 处理说明；受访者可拒绝 AI 追问。
- **安全**：前端不包含模型 Key；问卷内容显示能抵御 XSS；密码不明文；对每项管理 API 执行所有者校验；公开 token 不可简单枚举。
- **稳定**：AI 失败不阻塞提交；数据库失败有清晰错误；网络请求超时不无限旋转；前端可显示加载/空结果/错误状态。
- **易用**：手机竖屏操作，填卷按钮可点击；浏览器后退不会意外提交；提交后确认成功；界面能够清晰区分“AI 建议”和“实际数据”。
- **研发严谨**：测试数据与真实数据分开；不使用公开可识别个人信息做演示；不编造“准确率提升 XX%”。

## 9. 最简验收记录模板

| 验收项 | 结果 | 证据 |
|---|---|---|
| Vue 3 / ECharts / Spring Boot / MyBatis-Plus | □通过 □失败 | `package.json`、`pom.xml`、Mapper 文件 |
| 前后端和 MySQL 运行 | □通过 □失败 | 健康检查 / DB 查询 |
| 当前阶段主要业务路径 | □通过 □失败 | 操作录屏 / 实际链接 |
| 数据与统计真实可复算 | □通过 □失败 | SQL、API、图表数值 |
| 异常与权限保护 | □通过 □失败 | 测试输出 |
| 自动测试 + 回归 | □通过 □失败 | 测试报告 |
| 交接证据完整 | □通过 □失败 | `evidence/Mx.md` |

**最后记住**：Agent 做完 ≠ 项目验收通过。你自己能重新启动、自己输入新测试数据、自己看到数据库和页面正确变化，才算真正通过。
